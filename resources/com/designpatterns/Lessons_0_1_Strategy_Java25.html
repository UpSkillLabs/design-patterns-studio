BEFORE YOU CODE

A small, explicit lab

You need basic Java methods, classes, constructors, and conditionals. This guide explains the additional syntax when it first appears. The runnable files use only the standard library.

Keep the domain small

Decision for this labWhy it is explicit
One currency; money is a long number of cents.10_000L means $100.00. No fractional cents enter shipping calculations.
Weight is a positive int in whole kilograms.Fractional weights and carrier rounding are outside this lesson.
Subtotal is nonnegative and excludes shipping.The workflow is simply subtotal plus shipping.
Remote destination is a boolean.We retain the original variation without building an address model.
No tax, currency conversion, carrier API, or persistence.These would introduce independent design problems.

The L suffix makes a number a long; underscores improve readability. Multiplication by a long constant also makes the rate calculation use long arithmetic. The largest positive int weight is safe at these rates.

LESSON 0 / 01

One requirement. One algorithm.

“Calculate shipping price at $2 per kilogram.”

Start with a method. It takes what the calculation needs and returns the result. There is no reason yet for a shipping interface, registry, or class hierarchy.

SimpleShipping.java · first implementation
static long firstShippingCents(int weightKg) {
    if (weightKg <= 0) {
        throw new IllegalArgumentException("Weight must be positive");
    }
    return weightKg * 200L;
}

At 10 kg, the result is 2_000 cents. The validation is a domain rule; it does not imply a design pattern.

The first change is still simple

“Support standard and express shipping.”

SimpleShipping.java · second implementation
static long shippingCents(int weightKg, String method) {
    if (weightKg <= 0) {
        throw new IllegalArgumentException("Weight must be positive");
    }
    if ("standard".equals(method)) {
        return weightKg * 200L;
    }
    if ("express".equals(method)) {
        return weightKg * 400L + 1_000L;
    }
    throw new IllegalArgumentException("Unknown method: " + method);
}

"standard".equals(method) compares string contents and safely returns false for null. Unknown or missing method names reach the explicit error. A string is enough for the teaching example; request parsing can validate it at the application boundary.

Do not refactor on sight

An if is not evidence of bad design. Two short, stable branches may be the easiest code to understand and maintain.

Try it

Run SimpleShipping. Predict both prices for 3 kg, then change the input and check: standard is 600 cents; express is 2,200 cents.

LESSON 0 / 02

Let the requirements create pressure

“Standard has a discount. Express and overnight have different remote-area surcharges. More shipping methods are coming.”

MethodRule, in cents
StandardweightKg × 200; subtract 500 if subtotal is strictly greater than 10,000; minimum price 0.
ExpressweightKg × 400 + 1,000; add 1,500 for remote delivery.
OvernightweightKg × 700 + 2,500; add 3,000 for remote delivery.
Make the behavior correction before refactoring

The original discount can make shipping negative: 1 kg gives 200 − 500 = −300 cents. This guide adds a zero minimum to the baseline before moving code. The later refactor preserves that baseline, including its discounts and remote surcharges.

The expanded method now owns several independently changing policies:

StrategyLab.java · baseline before refactoring
static long shippingBefore(Order order, String method) {
    Objects.requireNonNull(order, "order");
    if ("standard".equals(method)) {
        long price = order.weightKg() * 200L;
        if (order.subtotalCents() > 10_000L) {
            price -= 500L;
        }
        return Math.max(0L, price);
    }
    if ("express".equals(method)) {
        long price = order.weightKg() * 400L + 1_000L;
        if (order.remote()) {
            price += 1_500L;
        }
        return price;
    }
    if ("overnight".equals(method)) {
        long price = order.weightKg() * 700L + 2_500L;
        if (order.remote()) {
            price += 3_000L;
        }
        return price;
    }
    throw new IllegalArgumentException("Unknown method: " + method);
}

International delivery, store pickup, same-day delivery, and partner delivery would add further policies. Three are enough to expose the pressure; there is no magic number of branches that requires a pattern.

LESSON 0 / 03

Find the axis of change

The problem is not simply that the method is getting long. Standard discounts, express fees, and overnight surcharges can change for different business reasons, yet every change enters the same method.

Sharing a method does not automatically make algorithms depend on each other. Here it creates a common editing and reasoning surface: a maintainer must navigate unrelated rules, and the caller remains tied to the combined selector and calculator.

Ask two questions before introducing a type

What remains stable?What varies independently?
Checkout asks for a shipping price and adds it to the subtotal.Each shipping method calculates its price differently and can evolve separately.

The axis of change is the shipping calculation. The boundary should let checkout ask for that capability without knowing each formula.

Five ideas, grounded in this example

ConceptMeaning hereDesign question
CohesionA module's code serves one related purpose.Do standard discount rules belong with standard pricing?
CouplingHow much one part relies on another's details.Must checkout change when express pricing changes?
DependencyA type, value, or behavior needed by another part.What does checkout actually need to know?
AbstractionA contract that exposes useful behavior and hides details.Can “calculate shipping” be described without a formula?
CompositionAn object uses another object to do part of its work.Can we give checkout a calculator instead of putting every rule inside it?
The design decision

Separate the stable checkout workflow from the varying shipping calculation. Keep selecting a policy as a separate responsibility.

Pause before moving on

Explain the pressure without using the words “interface” or “Strategy.” If the problem statement already dictates a class diagram, step back.

LESSON 1 / 01

Describe the capability first

Checkout needs something that can calculate shipping. Start with the input data, then describe only that capability.

StrategyLab.java · immutable input data
record Order(int weightKg, long subtotalCents, boolean remote) {
    Order {
        if (weightKg <= 0 || subtotalCents < 0) {
            throw new IllegalArgumentException("Invalid order");
        }
    }
}

A Java record declares a data carrier. Java generates the constructor and accessors such as weightKg(); its component fields are final. The compact constructor checks the inputs. With only primitive components, this particular record has no mutable nested state. [3]

StrategyLab.java · the dependency boundary
@FunctionalInterface
interface ShippingPolicy {
    long calculateCents(Order order);
}

The contract names an operation, not an implementation. Checkout will know ShippingPolicy, not ExpressShipping.

The signature is only part of the contract

Contract elementAgreement
InputA non-null, valid Order.
OutputA nonnegative shipping amount in the same currency's cents.
Behavior in this labReturn a quote; do not change the order or perform I/O.
Caller responsibilitySupply a valid order and handle a failed calculation if a future implementation can fail.

@FunctionalInterface asks the compiler to verify that the interface is functional. Here there is one abstract method, so a lambda can supply it too. The annotation is useful but is not required for lambda compatibility. [4]

A useful boundary has a narrow purpose

Do not add tracking, label printing, payment, or persistence to ShippingPolicy. Checkout asked for a shipping price.

In a larger codebase, keep this contract with the application/domain code that needs it, so callers do not have to import an implementation module. Our single-file lab nests types only to keep setup small.

LESSON 1 / 02

Move each algorithm intact

Give each policy one place to change. Preserve the rules while moving them; a structural refactor should not silently alter prices.

StrategyLab.java · the three implementations
static final class StandardShipping implements ShippingPolicy {
    @Override
    public long calculateCents(Order order) {
        long price = order.weightKg() * 200L;
        if (order.subtotalCents() > 10_000L) {
            price -= 500L;
        }
        return Math.max(0L, price);
    }
}

static final class ExpressShipping implements ShippingPolicy {
    @Override
    public long calculateCents(Order order) {
        long price = order.weightKg() * 400L + 1_000L;
        return price + (order.remote() ? 1_500L : 0L);
    }
}

static final class OvernightShipping implements ShippingPolicy {
    @Override
    public long calculateCents(Order order) {
        long price = order.weightKg() * 700L + 2_500L;
        return price + (order.remote() ? 3_000L : 0L);
    }
}

implements ShippingPolicy establishes the contract. @Override lets the compiler check that each method implements the expected operation. The implementations are public because an interface's abstract methods are public.

static means these nested classes do not need a StrategyLab instance. In an application you can place the types in separate files. final prevents subclassing; variation is provided through the shared interface.

Keep the right conditionals

The subtotal check belongs inside standard pricing. The remote-area check belongs inside the relevant delivery policy. Strategy does not require eliminating those decisions.

Predict the edit

If the remote express surcharge changes from $15 to $18, which calculation changes? Which regression checks should change? Checkout should have no pricing edit.

LESSON 1 / 03

Give checkout the capability

The checkout service receives a policy through its constructor, stores it, and delegates the calculation. This is object composition.

StrategyLab.java · stable workflow
static final class CheckoutService {
    private final ShippingPolicy shippingPolicy;

    CheckoutService(ShippingPolicy shippingPolicy) {
        this.shippingPolicy = Objects.requireNonNull(shippingPolicy);
    }

    long totalCents(Order order) {
        Objects.requireNonNull(order, "order");
        long shipping = shippingPolicy.calculateCents(order);
        if (shipping < 0) {
            throw new IllegalStateException("Negative shipping");
        }
        return Math.addExact(order.subtotalCents(), shipping);
    }
}

The constructor rejects a missing policy. Checkout rejects negative shipping and uses Math.addExact to throw ArithmeticException if the total overflows a long. [5]

THE DEPENDENCY BOUNDARY

CheckoutService→ShippingPolicy←Shipping implementations

Arrows mean “depends on the contract.” The runtime object is still a concrete policy.

Trace one call

Inside StrategyLab · composition example
ShippingPolicy policy = new ExpressShipping();
CheckoutService checkout = new CheckoutService(policy);
long total = checkout.totalCents(new Order(10, 10_000L, false));
// 10_000 + (10 * 400 + 1_000) = 15_000 cents

Checkout invokes the interface method. Java dispatches that call to the actual ExpressShipping object; checkout then adds its 5,000-cent result to the subtotal.

Now name the design: Strategy

Strategy puts interchangeable algorithms behind a common contract so a context can use the selected algorithm. Here the context is CheckoutService, the strategy contract is ShippingPolicy, and the concrete strategies calculate shipping.

Supplying the constructor parameter is manual dependency injection. Depending on this contract illustrates dependency inversion. No framework is needed. The final field fixes a policy per instance; Strategy does not require changing it later.

LESSON 1 / 04

Someone still has to choose

“The request says express. Which object should be used?”

Strategy separates calculation from selection. A small selector near the application entry point translates an external method name into an implementation.

StrategyLab.java · selection boundary
static ShippingPolicy selectPolicy(String method) {
    if (method == null) {
        throw new IllegalArgumentException("Method is required");
    }
    return switch (method) {
        case "standard" -> new StandardShipping();
        case "express" -> new ExpressShipping();
        case "overnight" -> new OvernightShipping();
        default -> throw new IllegalArgumentException(
                "Unknown method: " + method);
    };
}

This Java switch expression returns an object. Arrow cases do not fall through; default rejects unsupported names. The null check makes the failure explicit. Names are case-sensitive in this lab. [6]

Inside StrategyLab · application wiring
String requestedMethod = "express"; // From a validated request.
ShippingPolicy policy = selectPolicy(requestedMethod);
CheckoutService checkout = new CheckoutService(policy);
long total = checkout.totalCents(new Order(10, 10_000L, false));
ResponsibilityOwnerWhat it knows
SelectionselectPolicySupported names and concrete types.
CalculationEach shipping implementationIts business rules and required order data.
WorkflowCheckoutServiceThe contract and how to combine subtotal with shipping.
Moving a decision is a real design change

There is still a conditional, but it chooses an algorithm instead of containing every algorithm. Keep this wiring centralized; repeating this switch in every caller would recreate a maintenance problem.

This helper is a simple factory-style selector. It does not, by itself, demonstrate the GoF Factory Method pattern, which has a different construction structure. We will derive creation patterns when creation itself becomes the pressure.

Check three levels

  1. Policy checks: rate, discount threshold, remote surcharge, and zero minimum.
  2. Workflow checks: a fixed policy result is included; invalid results and overflow are rejected.
  3. Wiring checks: a selected express policy produces the expected total; unsupported names fail.

LESSON 1 / 07

What changed, and what did it cost?

Design concernBeforeAfter
Change express pricingEdit a combined method.Edit the express policy and its expectations.
Add another algorithmAdd another calculation branch.Add an implementation; update selection if publicly exposed.

Use the boundary when it contains real change

Strategy is useful when several algorithms vary independently, callers should not know their details, and substitution or separate testing is valuable. The cost is additional types or functions, indirection, wiring, and debugging navigation.

Keep a conditional when there are only a few short, stable rules. Keep a single parameterized function when only a rate varies. A family of one-line classes can be more ceremony than insight.

Inside StrategyLab · Strategy can be a function
ShippingPolicy fixedFee = order -> 750L;
CheckoutService checkout = new CheckoutService(fixedFee);

A lambda is useful for short behavior without extra state. A named class is useful when an algorithm has substantial logic, collaborators, or a domain name worth navigating to. Both can implement the same design.

Common wrong turns

  • Checkout chooses its own concrete policy. That makes selection a checkout responsibility again.
  • Checkout checks instanceof ExpressShipping. That leaks concrete-policy knowledge back into the workflow.
  • A new class means no other edits. Selection, configuration, and tests can still change.
  • The interface guarantees identical semantics. Implementations must honor the same units, validity rules, and behavioral contract.
  • More interfaces means better design. Every abstraction has to earn its cost.
The principle to retain

Use the simplest design that contains the change you have evidence to expect. Separate independently changing policies; keep local decisions close to the rules they express.

YOUR LAB / DISCOUNTS

Derive the boundary yourself

Start with the same pressure in a different part of checkout. The original example returns a discount amount, not the final total.

DiscountLab.java · starting implementation
static long discountBefore(String type, long amountCents) {
    if ("regular".equals(type)) {
        return percentOf(amountCents, 5);
    }
    if ("premium".equals(type)) {
        return percentOf(amountCents, 10);
    }
    if ("employee".equals(type)) {
        return percentOf(amountCents, 30);
    }
    return percentOf(amountCents, 0);
}

percentOf(amountCents, percent) calculates a whole percentage in cents and rounds a fractional cent down. For nonnegative integers, division by 100 discards the remainder. The complete helper rejects negative input and uses checked multiplication. [6] [5]

Write the design before the classes

  1. What varies independently?
  2. What remains stable?
  3. What capability does checkout need?
  4. Where should that contract live?
  5. Who should choose the implementation?
  6. Can student discount be added without modifying checkout?
  7. Can the rules and workflow be tested independently?

YOUR LAB / REVIEW AFTER YOUR ATTEMPT

One possible answer

Design reasoning and solution outline

Variation: the discount rule. Stable work: calculate the amount due. Capability: return the discount in cents for an amount. Put that contract with the caller's application/domain code; select the implementation at the entry point.

Inside DiscountLab · contract and wiring
@FunctionalInterface
interface DiscountPolicy {
    long discountCents(long amountCents);
}

DiscountPolicy premium = amount -> percentOf(amount, 10);
Checkout checkout = new Checkout(premium);
long due = checkout.totalCents(10_000L); // 9_000 cents

The reference solution uses lambdas because these policies differ only by a percentage. Separate RegularDiscount, PremiumDiscount, and EmployeeDiscount classes would also be valid practice, especially if their rules later diverge.

DiscountLab.java · the stable caller
static final class Checkout {
    private final DiscountPolicy discountPolicy;

    Checkout(DiscountPolicy discountPolicy) {
        this.discountPolicy = Objects.requireNonNull(discountPolicy);
    }

    long totalCents(long amountCents) {
        if (amountCents < 0) {
            throw new IllegalArgumentException("Negative amount");
        }
        long discount = discountPolicy.discountCents(amountCents);
        if (discount < 0 || discount > amountCents) {
            throw new IllegalStateException("Invalid discount");
        }
        return amountCents - discount;
    }
}

The selector retains a zero-discount fallback. The helper returns Math.multiplyExact(amountCents, percent) / 100L. If the multiplication overflows, the lab throws rather than returning a corrupted price. A broader monetary model would need its own representation and rounding decisions.

Student: supply amount -> percentOf(amount, 15). No checkout edit is needed. Add a selection branch if requests must choose "student" by name.

The complete DiscountLab.java appendix includes the initial implementation, selector, helper, checkout, and runnable checks.

What to learn next

If object creation and selection spread across callers, investigate creation patterns next. If logging, insurance, and weekend surcharges must wrap multiple policies, investigate Decorator. Derive each from a new pressure in this same system.

RECALL / WITHOUT LOOKING AT THE CODE

Can you explain the design?

01

State the pressure

Several shipping policies change independently while checkout's workflow remains stable.

02

Name the boundary

A shipping policy takes a valid order and returns a nonnegative shipping amount in cents.

03

Locate the decisions

Entry-point wiring chooses the policy. Each policy owns its own pricing decisions. Checkout composes the result.

04

Show substitution

A real algorithm and a fixed-result test double can both satisfy the contract.

05

State the cost

More structure and navigation. An interface change can affect every implementation.

06

Know when to stop

A short, stable conditional can be the better design. Extract the boundary when the observed change justifies it.

A refactoring checklist you can reuse

  1. Write down inputs, outputs, and error behavior.
  2. Identify independent reasons for change.
  3. Keep the stable workflow visible.
  4. Describe the smallest useful capability.
  5. Move one algorithm at a time without changing its rules.
  6. Choose implementations at a clear boundary.
  7. Check policy behavior, substitution, and wiring.
  8. Compare the maintenance benefit with the added indirection.

The point is not to recognize a class diagram.
It is to explain why a boundary belongs there.

        return Math.addExact(order.subtotalCents(), shipping);
    }
}

static ShippingPolicy selectPolicy(String method) {
    if (method == null) {
        throw new IllegalArgumentException("Method is required");
    }
    return switch (method) {
        case "standard" -> new StandardShipping();
        case "express" -> new ExpressShipping();
        case "overnight" -> new OvernightShipping();
        default -> throw new IllegalArgumentException(
                "Unknown method: " + method);
    };
}

static final class DroneShipping implements ShippingPolicy {
    @Override
    public long calculateCents(Order order) {
        return 2_000L + order.weightKg() * 500L;
    }
}

    if (expected != actual) {
        throw new AssertionError(label + ": expected " + expected
                + ", got " + actual);
    }
}

public class DiscountLab {
    @FunctionalInterface
    interface DiscountPolicy {
        long discountCents(long amountCents);
    }

    // Whole percentages, with fractional cents rounded down.
    static long percentOf(long amountCents, int percent) {
        if (amountCents < 0 || percent < 0 || percent > 100) {
            throw new IllegalArgumentException("Invalid discount input");
        }
        return Math.multiplyExact(amountCents, percent) / 100L;
    }

    static long discountBefore(String type, long amountCents) {
        if ("regular".equals(type)) {
            return percentOf(amountCents, 5);
        }
        if ("premium".equals(type)) {
            return percentOf(amountCents, 10);
        }
        if ("employee".equals(type)) {
            return percentOf(amountCents, 30);
        }
        return percentOf(amountCents, 0);
    }

    static DiscountPolicy selectDiscount(String type) {
        if ("regular".equals(type)) {
            return amount -> percentOf(amount, 5);
        }
        if ("premium".equals(type)) {
            return amount -> percentOf(amount, 10);
        }
        if ("employee".equals(type)) {
            return amount -> percentOf(amount, 30);
        }
        return amount -> percentOf(amount, 0);

static final class Checkout {
        private final DiscountPolicy discountPolicy;

        Checkout(DiscountPolicy discountPolicy) {
            this.discountPolicy = Objects.requireNonNull(discountPolicy);
        }

        long totalCents(long amountCents) {
            if (amountCents < 0) {
                throw new IllegalArgumentException("Negative amount");
            }
            long discount = discountPolicy.discountCents(amountCents);
            if (discount < 0 || discount > amountCents) {
                throw new IllegalStateException("Invalid discount");
            }
            return amountCents - discount;
        }
    }

    static void equal(long expected, long actual) {
        if (expected != actual) {
            throw new AssertionError("Expected " + expected + ", got " + actual);
        }
    }

    public static void main(String[] args) {
        String[] types = {"regular", "premium", "employee", "guest", null};
        long[] discounts = {500L, 1_000L, 3_000L, 0L, 0L};
        for (int i = 0; i < types.length; i++) {
            DiscountPolicy policy = selectDiscount(types[i]);
            equal(discounts[i], discountBefore(types[i], 10_000L));
            equal(discounts[i], policy.discountCents(10_000L));
            equal(10_000L - discounts[i], new Checkout(policy)
                    .totalCents(10_000L));
        }
        equal(0L, selectDiscount("regular").discountCents(0L));
        equal(49L, selectDiscount("regular").discountCents(999L));
        equal(9_000L, new Checkout(amount -> 1_000L).totalCents(10_000L));
        DiscountPolicy student = amount -> percentOf(amount, 15);
        equal(8_500L, new Checkout(student).totalCents(10_000L));
        System.out.println("All discount checks passed.");
        System.out.println("Student total: 8500 cents");
    }
}
