Part 01 · Sections 1–8

Derive the problem

From a business fact to a durable publication obligation.

01Start with the business requirement

A customer’s payment has been confirmed. The ordering service must record the order as paid, and Shipping must eventually learn about it. The two services have separate storage and communicate through a broker.

The local use case is PayOrder; the event is OrderPaid. Here, “pay” means recording a confirmed payment. Charging a payment provider is another external boundary, examined in §28.

Ask first: which facts must agree? If an order becomes paid, the obligation to notify Shipping must survive a process crash. If the order does not become paid, we must not announce that it did.

FactOwner
Order is paidOrdering database
OrderPaid is available to other servicesMessage broker
Shipment existsShipping database

02The straightforward implementation

We naturally write two operations: commit the order, then publish its event. Each operation may be correct by itself. Their composition is the problem.

Java
// Deliberately unsafe sketch: the operations commit independently.
orders.save(order);
publisher.publish(event);

A database transaction can group database writes. A normal database transaction does not automatically make a separate broker call atomic with those writes.

03Database first: a missing event

The order update commits. Before publication, the application crashes. On restart the database says PAID, but no durable record tells the application that publication is still required.

StepResult
1. Commit order updateOrder is PAID
2. Process crashesPublish call never happens
3. RecoverShipping may never learn about the payment

A try/catch block does not run after the process has disappeared. The recovery information must already be durable.

04Broker first: a false fact

Reverse the calls. The broker accepts OrderPaid, then the database update fails or rolls back. Shipping can now act on an event whose corresponding business change never committed.

OrderingCrash window
Commit → publishPaid order, missing event
Publish → commitPublished event, unpaid order

Reordering the operations changes the failure. It does not remove the gap.

05A local transaction does not cover the network

Putting a broker call between BEGIN and COMMIT does not enlist the broker in that database transaction. A broker success cannot be undone merely by rolling back the database.

Waiting for both operations to succeed improves the happy path, but the crash points remain. We need to identify the actual atomic boundary rather than infer it from the placement of code.

Question to carry forward

What can the application commit together, using one resource that already provides transactions?

06After-commit callbacks still have a gap

An after-commit callback avoids publishing a fact before its transaction commits. But the process can die after commit and before the callback executes. An in-memory event bus or a background task has the same durability limit.

A “retry later” instruction helps only if something persistent remembers what to retry. We need a durable obligation, not just a convenient place to call the publisher.

07Move the obligation inside the transaction

Instead of requiring “update the order and publish the event atomically,” require “update the order and record that this event must be published atomically.” Both writes can live in the ordering database.

SQL · transaction shape
BEGIN;
UPDATE orders SET status = 'PAID' WHERE id = ?;
INSERT INTO outbox_message (...) VALUES (...);
COMMIT;

The row is a durable promise. A separate process can read it after commit and keep trying to fulfil that promise.

08Derive the invariant before naming the pattern

For a new payment transition, the database exposes one of two outcomes:

Transaction outcomeOrderPublication obligation
CommitsPAIDOutbox event exists
Rolls backPrevious stateNo new outbox event

We replaced publish the message atomically with record the obligation to publish atomically. We have derived the Transactional Outbox.

Part 02 · Sections 9–12

Make the local change atomic

The outbox, schema, transaction, and architectural responsibility.

09Transactional Outbox

The application writes the order and the outbox row in one local transaction. A message relay publishes committed outbox rows later. Shipping remains downstream of the broker.

Atomic · producer database

Order update + outbox insert

Commit the fact and its publication obligation together.

Asynchronous · network

Relay → broker → Shipping

Publish after commit. Recover with retry.

The outbox row is visible to the relay only after commit. This separates local correctness from broker availability. AWS’s outbox guidance describes the same dual-write problem and the need to handle duplicate delivery. AWS · Transactional outbox

10A small, explicit schema

The lesson’s smallest outbox needs an ID, type, aggregate ID, payload, occurrence time, and publication marker. This guide includes schema and aggregate versions from the start so the code and later ordering discussion use one consistent model.

PostgreSQL 18
CREATE TABLE orders (
    id UUID PRIMARY KEY,
    status VARCHAR(20) NOT NULL
        CHECK (status IN ('PENDING', 'PAID', 'CANCELLED')),
    version BIGINT NOT NULL DEFAULT 0 CHECK (version >= 0)
);

CREATE TABLE outbox_message (
    id UUID PRIMARY KEY,
    event_type VARCHAR(200) NOT NULL,
    event_version INTEGER NOT NULL,
    aggregate_id UUID NOT NULL,
    aggregate_version BIGINT NOT NULL,
    payload JSONB NOT NULL,
    occurred_at TIMESTAMPTZ NOT NULL,
    published_at TIMESTAMPTZ
);

CREATE INDEX idx_outbox_unpublished
    ON outbox_message (occurred_at, id)
    WHERE published_at IS NULL;

published_at IS NULL means publication has not been durably recorded as complete. It does not prove the broker has never received the event.

The outbox is a durable handoff mechanism. It need not be an event store, and the orders table can remain the business source of truth. The index’s timestamp order is a polling convenience, not a guarantee of causal order.

11Make the application transaction explicit

The key constraint is physical: orders.save and outbox.add must use the same connection and transaction. Passing that connection explicitly makes the boundary visible in this teaching example.

Java
public record PayOrderHandler(
        TransactionRunner transactions, OrderRepository orders,
        OutboxRepository outbox, Clock clock) {

    public void handle(PayOrder command) throws SQLException {
        transactions.inTransaction(c -> {
            Order order = orders.findForUpdate(c, command.orderId())
                    .orElseThrow(() ->
                            new IllegalArgumentException("Missing order"));
            if (!order.markPaid()) return null;
            orders.save(c, order);
            OrderPaid event = new OrderPaid(
                    UUID.randomUUID(), order.id(),
                    order.version(), clock.instant());
            outbox.add(c, OutboxMessage.from(event));
            return null;
        });
    }
}

findForUpdate locks the order row until the transaction ends. The domain’s markPaid() rejects cancelled orders and returns false for an already-paid order. With the lock, two concurrent commands cannot both generate a new event for this one-way transition. PostgreSQL 18 · Explicit locking

The event ID is created once for the successful transition, then stored with its payload. A failed transaction may create a new ID on a later attempt because the previous event never became visible.

Command retries are a separate problem

An outbox does not deduplicate incoming commands. This example makes “mark this order paid once” idempotent under a row lock. Workflows allowing repeated payments need a durable command or payment ID and an explicit result record.

JDBC connections default to auto-commit. The reference runner disables it, commits after the callback, and attempts rollback on failure. The repositories do not commit independently. Java 25 · Connection

The full definitions of the domain, ports, transaction runner, and handler are included in Appendix A.

12What improved architecturally?

Before, the application use case directly coordinated two independently failing technologies. Its correctness depended on the combined database and broker outcomes.

OwnerResponsibility
Application transactionValidate and persist the business change plus its durable consequences
Message relayPublication, retries, broker failures, publication bookkeeping
Consumer transactionApply a local effect safely despite redelivery

These responsibilities change for different reasons. The handler no longer needs a successful broker call to commit a paid order. This is useful only when the business permits asynchronous propagation.

The domain still knows nothing about Kafka. A composition root supplies database repositories and a broker publisher through explicit ports.

Part 03 · Sections 13–18

Make the handoff recoverable

Relay failure windows explain retries, duplicates, and stable IDs.

13The first relay—and its new failure window

One worker reads pending rows, publishes each message, then marks it published. The critical sequence is small:

Java
publisher.publishAndAwaitAcceptance(message);
outbox.markPublished(message.id(), clock.instant());

The publisher’s contract must mean broker acceptance under the configured durability policy. Returning after adding a message to a local client buffer is insufficient. Kafka’s send is asynchronous; an adapter must observe completion and handle failure before marking the row. Apache Kafka 4.1 · KafkaProducer API

Polling once per second is an illustrative choice. A scheduled task must handle expected exceptions: an exception escaping a periodic task suppresses later executions in Java’s scheduler. Java 25 · ScheduledExecutorService

A second dual write remains

Publish and mark-published are still separate operations. We have arranged the remaining gap so recovery can retry a durable message, instead of forgetting it. The complete relay in Appendix A logs failures, preserves interruption, and assumes one worker.

The relay must reuse the committed event envelope. It must not rebuild a fresh business event on each poll.

14Failure: the broker is unavailable

The relay cannot obtain a successful publication result, so it does not mark the row. The event remains pending.

Once the broker recovers, the relay retries the same stored message. The application could continue accepting local business transactions during the outage, subject to database capacity and any chosen backlog limits.

What survived?

The committed order and the durable publication obligation. Neither depends on the relay process staying alive.

15Failure: publish succeeds, then the relay crashes

The broker accepts event abc123. Before the relay commits published_at, it crashes. The database still presents that row as pending.

AttemptBrokerOutbox
First publicationAccepts abc123Still pending at crash
Recovery publicationMay accept abc123 againMarked published after acceptance

A duplicate is possible even if the initial send succeeded. A timeout or a lost acknowledgement creates the same uncertainty: the relay may not know whether the broker accepted the message.

16Why not mark it published first?

If the relay commits the marker first and then crashes before sending, future polls skip a message that was never published.

SequenceCrash consequenceChosen semantics
Publish → markPossible duplicateRetry pending work
Mark → publishPossible permanent lossWork may be forgotten

For a business event that must not disappear, choose publish before mark and make duplicates safe downstream. This is the trade that leads to at-least-once delivery.

17What at-least-once actually promises

A delivered event may arrive more than once; it need not be duplicated in ordinary operation. The ambiguity is unavoidable for this uncoordinated boundary: a failed attempt and a successful attempt with a lost response can look the same to the sender.

Retry chooses possible duplication over possible loss. That is a failure policy, not an unconditional liveness guarantee.

State the assumptions

Eventual delivery requires retained durable state, a functioning relay, eventual destination availability, successful handling of the payload, and continued retries or operator recovery. A permanently failed message placed in quarantine has not been delivered.

Broker acceptance, consumer delivery, and successful business processing are separate milestones. Marking an outbox row published proves only the first milestone under the publisher’s stated contract.

18Retries require stable message identity

Create eventId when inserting the outbox row. Every retry sends that ID and the same event content. A deduplicating consumer can then recognize repeated deliveries.

CorrectIncorrect
abc123 → abc123 → abc123abc123 → def456 → ghi789
One event, several delivery attemptsSeveral identities for the same fact

An event ID identifies an occurrence. An aggregate ID identifies the order. A command ID identifies an incoming request. These identities solve different problems.

Do not mutate history during retries

Use a versioned event schema and an immutable stored payload. An intentional correction should be a new event; redelivery of the original keeps its original ID.

Part 04 · Sections 19–26

Make the local effect safe

Idempotency, Inbox, and acknowledgement after commit.

19The consumer now receives duplicates

Shipping receives OrderPaid(abc123) twice. If its handler unconditionally creates a shipment, one payment can create two shipments.

The producer outbox solved the relationship between the order update and publication intent. It did not make downstream processing duplicate-safe. Distributed correctness is an end-to-end property.

The next question is not “how can we wish away redelivery?” It is “how can the receiver make repeated processing harmless?”

20First choice: a naturally idempotent effect

An idempotent operation has the same effective result when repeated. If the business permits exactly one shipment per order, encode that rule in the database:

PostgreSQL 18
CREATE TABLE shipment (
    id UUID PRIMARY KEY,
    order_id UUID NOT NULL UNIQUE
);

INSERT INTO shipment (id, order_id)
VALUES (?, ?)
ON CONFLICT (order_id) DO NOTHING;

The first delivery creates the shipment; a duplicate leaves the same one-shipment state. The unique constraint handles concurrent attempts. A separate “does it exist?” query followed by an unconstrained insert would race. PostgreSQL 18 · INSERT

This is the simplest solution when it matches the real business invariant. If partial shipments are allowed, UNIQUE(order_id) is the wrong rule. Choose the actual business identity.

21Some effects accumulate

Adding loyalty points is not naturally idempotent:

DeliveryEffectTotal added
OrderPaid abc123Add 100 points100
Duplicate abc123Add 100 points again200

We need to remember whether this particular consumer already applied this particular message. That memory must survive restarts and concurrent processing.

A durable, uniquely keyed loyalty-credit ledger can also solve this. A generic processed-message record is useful when the effect spans several local writes.

22Derive the Inbox pattern

Record a processed-message identity in the receiving database.

PostgreSQL 18
CREATE TABLE inbox_message (
    consumer_name VARCHAR(200) NOT NULL,
    message_id UUID NOT NULL,
    processed_at TIMESTAMPTZ NOT NULL,
    PRIMARY KEY (consumer_name, message_id)
);

The identity is (consumer_name, message_id). Shipping having processed an event does not imply that Loyalty or Analytics has processed it.

Use a stable logical consumer name, shared across replicas. A new random name per process defeats deduplication. Renaming a consumer or deleting its inbox history can cause old messages to be applied again; treat either as a replay decision.

23The consumer transaction

Insert the inbox identity and apply the business effect in the same local transaction. The unique key arbitrates concurrent deliveries.

Java
public record OrderPaidConsumer(
        TransactionRunner transactions, InboxRepository inbox,
        LoyaltyRepository loyalty) {

    public void handle(OrderPaid event) throws SQLException {
        transactions.inTransaction(c -> {
            boolean firstTime = inbox.tryInsert(
                    c, "loyalty-order-paid-v1", event.eventId());
            if (!firstTime) return null;
            loyalty.addPointsForOrder(c, event.orderId(), 100);
            return null;
        });
        // Broker adapter acknowledges only after handle returns.
    }
}

tryInsert uses ON CONFLICT (consumer_name, message_id) DO NOTHING and checks whether one row was inserted. It does not swallow unrelated constraint failures. PostgreSQL 18 · INSERT

The loyalty adapter resolves the order’s customer and adds points using the supplied connection. A missing target must fail the transaction; silently updating zero rows and committing the inbox would lose the effect.

24Why the Inbox and effect must commit together

Committing the inbox first and adding points later creates another lost-effect window. A crash between those commits leaves a permanent “processed” marker for work that never happened.

One transactionOutcome
Inbox insert succeeds; effect failsRoll back both
Inbox insert and effect succeedCommit both
Duplicate identity conflictsSkip the effect; commit the no-op

An uncommitted inbox insert is not a claim that processing is complete. It becomes a durable processed marker only when the business effect commits beside it.

The same principle appears twice

Related correctness state should share one atomic boundary whenever possible. First: order plus outbox. Now: inbox plus local effect.

25Acknowledge after the consumer commit

The broker adapter delivers the event, calls the consumer, and acknowledges only after the database transaction succeeds. If the process crashes after commit but before acknowledgement, redelivery finds the inbox identity and skips the effect.

Crash pointDurable consumer stateRecovery
Before DB commitNeither inbox nor effect committedProcess the redelivery
After DB commit, before ACKInbox and effect committedSkip duplicate effect, then ACK

For Kafka, the corresponding action is committing the consumer offset. Disable automatic offset advancement that can acknowledge work prematurely. A partition offset covers a position in the stream: do not commit past earlier unfinished records when processing concurrently. Apache Kafka 4.1 · KafkaConsumer API

The useful guarantee is a deduplicated local business effect. Messages may still be delivered and handler code invoked multiple times.

26The end-to-end design

1 · producer database

Fact + obligation

Commit the order change and outbox event together.

2 · broker boundary

Publish + retry

Send the stable event. Duplicate publication and delivery are possible.

3 · consumer database

Identity + effect

Commit the inbox identity and business effect together.

The architecture contains failure in places where retry can be made safe. It does not remove crashes, delays, ambiguous responses, or the need to operate the system.

Part 05 · Sections 27–31

Own recovery in production

Failure analysis, external effects, worker coordination, and operations.

27Use a failure matrix, not a pattern slogan

At each crash point, ask what is durable and what recovery will do. A pattern name is not evidence that a guarantee is implemented.

FailureDurable stateRecovery
Domain validation failsNo new order or outbox commitReject the command
Order update failsTransaction rolls backRetry only if the cause is recoverable
Outbox insert failsOrder update rolls back tooFix the cause; retry the transaction
Commit is definitively rolled backNeither new fact commitsRetry if appropriate
Commit response is lost / outcome unknownBoth may have committed, or neitherReconcile durable state; use an idempotent command retry

A commit exception does not always prove rollback. A lost connection can hide a successful commit. PostgreSQL distinguishes conditions such as statement completion unknown and transaction resolution unknown. Atomicity still holds in the database; the client’s knowledge is uncertain. 28An external effect creates another boundary

Suppose the consumer sends an email inside its database transaction. The email provider can accept the request, then the consumer can crash and roll back its inbox. A redelivery sends the email again. The database cannot undo that external effect.

A consumer-side outbox can atomically record an email obligation beside the inbox and local state. Its dispatcher then retries the email request. This prevents forgetting the obligation, but does not by itself prevent duplicate emails.

TechniqueWhat it achievesRemaining requirement
Consumer inbox + local state + email outbox in one DB transactionDurable, deduplicated creation of the email obligationDispatcher still has a send/mark gap
Stable provider idempotency keyCan deduplicate retried external requestsProvider must support the exact operation and retain the key for the retry window
Reconciliation / workflow stateResolves uncertain external outcomesRequires an authoritative status query or business recovery process

Use an effect-specific key such as abc123:receipt-email when one event produces multiple external actions. Keep the payload stable. Provider contracts vary; Stripe’s documented idempotency behavior is one concrete API example. Stripe · Idempotent requests

General rule

Every non-transactional boundary needs explicit failure semantics. Another outbox makes the handoff durable; the destination’s capabilities determine whether the final external effect can be deduplicated.

29Relay concurrency and row claiming

Several workers can read the same pending rows unless they coordinate. PostgreSQL can skip rows locked by another worker:

PostgreSQL 18 · locking approach
BEGIN;
SELECT *
FROM outbox_message
WHERE published_at IS NULL
ORDER BY occurred_at, id
LIMIT 100
FOR UPDATE SKIP LOCKED;
-- Publish selected messages; mark accepted messages.
COMMIT;

The locks only protect the selection while the transaction remains open. Committing immediately after this SELECT, without recording a claim, releases the protection. PostgreSQL describes SKIP LOCKED as suitable for queue-like access, not as a generally consistent view of the data. PostgreSQL 18 · SELECT

Keeping this transaction open during broker I/O holds locks and a connection. A scalable alternative is a short transaction that writes a lease and claim token, followed by publication outside the transaction.

State transitionCondition
PENDING → PROCESSINGClaim atomically; set owner/token and expiry
PROCESSING → PUBLISHEDBroker acceptance; update only with the current claim token
PROCESSING → eligible againLease expires before successful completion

A token prevents a stale worker from overwriting a newer claim. It cannot stop that stale worker from publishing after its lease expires. Duplicates remain possible. Bound network timeouts, choose lease duration deliberately, and add this complexity only when multiple workers or throughput require it.

30Operational ownership is part of the pattern

A pending table with no owner can quietly become a permanent backlog. Someone must be able to find failures, diagnose them, and recover them.

Data or signalQuestion it answers
Pending count and oldest pending ageAre we keeping up? How stale is propagation?
attempts, next_attempt_at, last_errorWhat failed, and when will it retry?
event_type and event_versionCan this consumer understand the payload?
aggregate_id and aggregate_versionWhich business object is affected?
claim_token and locked_until, if leasingWhich worker owns the current attempt?
Published retention and consumer inbox retentionCan we replay safely? What deduplication history remains?

Keep event schema version and aggregate version separate: one describes the payload contract; the other describes business sequence. Evolve both deliberately.

Retention is correctness-sensitive. Deleting inbox entries before the possible replay window ends re-enables duplicate effects. Deleting an outbox row before accepted publication can lose the obligation. Backlog limits and alerts should reflect the business tolerance for delay.

31Poison messages and deliberate recovery

A malformed payload, unsupported schema, or permanent destination rejection may never succeed. Retrying it every second forever creates noise and can block useful work.

Classify retryable and permanent failures. Use bounded exponential backoff with jitter for transient problems, then quarantine persistent failures with an alert and a recovery path. A dead-letter destination is a place to investigate, not evidence of successful business processing.

Persist a valid payload in the business transaction where possible. Even then, the relay can fail while mapping the envelope to a transport or a consumer can reject a new schema.

Retry policy and ordering interact

If per-order sequence is required, letting version 18 pass a quarantined version 17 can violate the contract. Decide whether to block that aggregate, reconcile it, or explicitly relax the requirement. The minimal relay stops a failed batch and does not implement production backoff or quarantine.

Part 06 · Sections 32–39

Define the limits of the guarantee

Ordering, exactly-once claims, and distributed transactions.

32Ask which ordering the business needs

Suppose one order emits version 7 OrderPaid and version 8 OrderShipped. A consumer whose logic depends on that sequence cannot safely treat arbitrary arrival order as causal order.

ScopeDesign implication
No orderingParallelism is easy; effects must tolerate arrival order
Per orderSerialize or validate effects for one order
Per customerA wider key coordinates several orders
Global orderEvery event shares one ordering requirement; often unnecessary

“Events must stay ordered” is not a complete requirement. Name the key, the events included, and the behavior when an earlier event is delayed or missing.

33Use logical sequence rather than wall-clock time

One transaction may create an event at 10:00:00.100 and commit at 10:00:03. Another creates an event at 10:00:00.200 and commits at 10:00:01. Timestamp order and visibility order differ; timestamps can also tie.

Java
public record OrderPaid(
        UUID eventId,
        UUID orderId,
        long orderVersion,
        Instant occurredAt) {}

A version assigned under the aggregate’s concurrency control expresses business sequence. occurredAt is useful context; it is not proof of causal order.

Versions are not automatically contiguous for every consumer

If only some aggregate changes emit events—or a consumer subscribes to only some event types—seeing versions 17 and 19 need not mean version 18 was lost. A next-version check requires an explicit complete stream or its own contiguous event sequence.

34Broker ordering has a scope

Kafka orders records within a partition. Under compatible partitioning, using a stable order ID as the message key routes that order’s events to the same partition. This does not create one global order. Apache Kafka 4.1 · Design

The relay can already violate the sequence: worker A claims order A version 17, worker B claims version 18, and B publishes first. The broker then correctly records the arrival sequence 18, 17.

A broker cannot repair a sequence the producer already inverted. Changes to partition routing also require care when the business relies on a stable per-key sequence.

35Ordering is end-to-end too

StageRequired decision when promising per-order sequence
DomainAssign a meaningful version under concurrency control
Outbox / relayDo not let a later event overtake an earlier one for that order
BrokerUse compatible partition routing and producer settings
ConsumerDo not apply the same key concurrently out of order
RecoveryDefine what to do with gaps, retries, duplicates, and poison messages

Possible recovery choices include waiting, retrying, fetching authoritative state, or reconciliation. An additive effect such as loyalty points has different needs from a state projection that replaces its current value.

The guide’s minimal polling relay deliberately makes no strict ordering promise. Sorting by timestamp and UUID is deterministic for a query but does not solve commit visibility, worker coordination, or retry ordering.

36Disambiguate “exactly once”

“Send the message exactly once” often hides several different requests. Be precise about the stage whose result matters.

Possible meaningWhat must be examined
One logical broker appendProducer retries and broker idempotence
One delivery or one handler invocationRedelivery and acknowledgement behavior
One local database effectTransaction boundaries and deduplication
One external charge or emailDestination idempotency and uncertain outcomes

A guarantee at one stage does not automatically extend to the others. Ask for the observable business outcome, then prove the path to it.

37Transport guarantees do not cover every business effect

Even if duplicate appends are prevented, a consumer can call an external service and crash before recording completion. The unresolved question is whether retrying will repeat that external effect.

Kafka’s transactional primitives support exactly-once processing in specified Kafka workflows, including consuming, processing, and writing results back to Kafka with the appropriate isolation and offset handling. External destinations require cooperation from those destinations. Apache Kafka 4.1 · Design

Therefore “we use Kafka exactly-once” is insufficient evidence that an email is sent or a card is charged once. State the actual resource boundary.

38Idempotent producers do not replace the outbox

A producer’s retry deduplication cannot help when the application commits PostgreSQL and crashes before invoking the producer at all. There is no broker request to deduplicate.

Likewise, committing a Kafka transaction does not automatically commit or roll back a separate PostgreSQL transaction. The outbox addresses the durable handoff from the local database; broker idempotence addresses supported producer retries.

These mechanisms can complement one another. Do not rely on producer idempotence to deduplicate every application-level resend of a stored outbox event. Apache Kafka 4.1 · KafkaProducer API

39Could distributed transactions solve it?

Two-phase commit coordinates participating resources through prepare and commit decisions. It requires suitable transaction infrastructure and compatible participants.

PostgreSQL supports prepared transactions intended for an external transaction manager. That support alone does not enlist an arbitrary broker or make a particular application stack a distributed transaction system. PostgreSQL 18 · Two-phase transactions

Coordination brings participant support requirements, resource retention while prepared, failure recovery, and operational coupling. The outbox instead commits local intent and accepts asynchronous retry.

Compare the actual contracts

Use distributed coordination when the required resources and operational model support it. Use an outbox when local atomicity plus asynchronous recovery fits the business. Neither choice erases its failure modes.

Prove the failure contract, then decide whether the cost fits.

40Test the transaction boundaries and crash windows

A mock verifying outbox.add() was called does not prove atomicity. Test durable outcomes after deliberately interrupting the sequence.

TestArrange / actAssert
1. Successful paymentExecute the handler against a real databasePAID and exactly one new outbox row
2. Outbox insertion failsMake the insert fail after the order updateOrder unchanged; no new outbox row
3. Domain rejectionPay a cancelled orderException; no business or outbox change
4. Broker unavailableReject a pending event, then restore acceptanceRow remains pending, then publishes
5. Publish succeeds; mark failsAccept event, fail marker write, rerun relaySame event ID may be published twice
6. Duplicate consumer deliveryDeliver the same ID twice, including concurrentlyOne inbox identity and one committed effect
7. Consumer effect failsInsert inbox, then force effect failureBoth roll back; later redelivery succeeds
8. Consumer ACK failsCommit consumer transaction, lose ACK, redeliverBusiness effect remains once
9. Concurrent relaysExercise real locking / lease behaviorDocumented claiming and recovery hold; duplicates still safe
10. Required orderingPublish versions under concurrency and failureExactly the promised ordering scope holds

Add command-retry tests for the handler in this guide: call it twice and race two calls for the same pending order. Both cases must create only one transition event. Also test uncertain commit responses and recovery with a new connection.

For leases, include expiry while an old worker is still alive. For retention, replay an old event at the edge of the deduplication window. These tests check actual promised behavior, not a stronger guarantee the design does not provide.

41Choose the test level that can expose the failure

LevelUseful coverage
UnitDomain transitions, event construction, retry classification, serialization mapping
Database integrationRollback, order/outbox atomicity, inbox/effect atomicity, constraints, locks, leases
SystemBroker outage, relay restart, consumer restart, offset/ACK behavior, duplicate delivery, ordering

The more a guarantee depends on locks, commit, network acknowledgement, or process death, the less convincing a pure mock test becomes.

The request must wait for an external reservationDesign a synchronous or explicit multi-step workflow
Infrastructure already covers the exact resources atomicallyUse and verify that actual transaction contract

An asynchronous event cannot satisfy a rule that requires confirmed external success before the request may succeed. An outbox can record an intent or a pending workflow state, but the application must expose that state honestly.

43The costs are real

The pattern adds a table, relay, retry policy, event identities, schema evolution, monitoring, retention, publication latency, and duplicate handling. Some systems also need an inbox, lease management, and ordering controls.

The temporal contract changes: the request commits local state and its obligation now; downstream propagation follows later. “Paid” and “Shipping has reacted” can be true at different times.

Patterns move complexity. Here, the useful move is from an unrecoverable dual-write gap to durable work plus explicit recovery. It is still your responsibility to keep that recovery working.

Explicit JDBC connections are a teaching choice that makes the boundary visible. A framework transaction manager or unit-of-work abstraction can express the same rule, provided both repositories truly share its transaction.

45The resulting dependency structure

ComponentDepends onOwns

The producer says: if my local transaction commits, the business fact and the obligation to propagate it are durable together. It does not require Kafka to be available at that instant.

The composition root must supply the producer ports with access to the same producer database and the consumer ports with access to the same consumer database. The two services’ databases need not be the same database.

46Re-derive the design from nine questions

  1. What facts must agree?
  2. Which facts can share one local transaction?
  3. What can fail independently outside that boundary?
  4. Can we durably record the obligation to cross it?
  5. Can the crossing be retried?
  6. Can retry produce duplicates?
  7. Can the receiver make repeated processing harmless?
  8. Is ordering required, and for which key?
  9. What is durable at every crash point, and what happens next?

These questions lead to local atomicity, an outbox, retry, at-least-once semantics, and an idempotent consumer or inbox. The pattern names come after the reasoning.

47The final correctness contract

BoundaryOperationsContract
Producer databaseDomain change + outbox insertAtomic local commit
Relay / brokerPublish + retry + markNo global atomicity; duplicates possible
Consumer databaseInbox insert + local effectAtomic local commit; duplicate effects suppressed
If the producer transaction commits, the event is durably scheduled for publication. Publication is retried and may occur more than once. Consumers are designed so repeated delivery of the same event does not repeat the committed local business effect.

This promise assumes retained data, eventual recovery, a valid event contract, correct transaction ownership, and a suitable deduplication window. It makes no automatic promise about arbitrary external effects or ordering.

That is a concrete contract you can test at each failure window.

A1 · Domain and immutable event

Java
public enum Status { PENDING, PAID, CANCELLED }

public record PayOrder(UUID orderId) {
    public PayOrder { Objects.requireNonNull(orderId); }
}

public record OrderPaid(
        UUID eventId, UUID orderId,
        long orderVersion, Instant occurredAt) {
    public OrderPaid {
        Objects.requireNonNull(eventId);
        Objects.requireNonNull(orderId);
        Objects.requireNonNull(occurredAt);
        if (orderVersion < 1) {
            throw new IllegalArgumentException("Invalid version");
        }
    }
}

public static final class Order {
    private final UUID id;
    private Status status;
    private long version;

    public Order(UUID id, Status status, long version) {
        this.id = Objects.requireNonNull(id);
        this.status = Objects.requireNonNull(status);
        if (version < 0) {
            throw new IllegalArgumentException("Invalid version");
        }
        this.version = version;
    }

    public boolean markPaid() {
        if (status == Status.CANCELLED) {
            throw new IllegalStateException("Order is cancelled");
        }
        if (status == Status.PAID) return false;
        long nextVersion = Math.incrementExact(version);
        status = Status.PAID;
        version = nextVersion;
        return true;
    }

    public UUID id() { return id; }
    public Status status() { return status; }
    public long version() { return version; }
}

A2 · Transaction runner

Java
@FunctionalInterface
public interface SqlWork<T> {
    T apply(Connection connection) throws SQLException;
}

public interface TransactionRunner {
    <T> T inTransaction(SqlWork<T> work) throws SQLException;
}

public record JdbcTransactions(DataSource dataSource)
        implements TransactionRunner {
    public JdbcTransactions { Objects.requireNonNull(dataSource); }

    @Override
    public <T> T inTransaction(SqlWork<T> work)
            throws SQLException {
        try (Connection c = dataSource.getConnection()) {
            c.setAutoCommit(false);
            try {
                T result = work.apply(c);
                c.commit();
                return result;
            } catch (SQLException | RuntimeException | Error ex) {
                try {
                    c.rollback();
                } catch (SQLException rollbackFailure) {
                    ex.addSuppressed(rollbackFailure);
                }
                throw ex;
            }
        }
    }
}
Runner contract

The runner owns a fresh connection for each call. Do not nest it inside another transaction or retain the callback’s connection. A pooled DataSource must reset connection state on reuse. Rollback failure is preserved as a suppressed exception. A commit or close exception can leave the caller uncertain about a transaction that committed; recovery must inspect durable state and use safe command semantics.

public interface OrderRepository {
    // Must SELECT ... FOR UPDATE on c, in this transaction.

            throws SQLException;
    // Persist status/version using c; never commit here.

}

public record OutboxMessage(
        UUID id, UUID aggregateId, long aggregateVersion,
        String eventType, int eventVersion,
        String payload, Instant occurredAt) {
    public OutboxMessage {
        Objects.requireNonNull(id);
        Objects.requireNonNull(aggregateId);
        Objects.requireNonNull(eventType);
        Objects.requireNonNull(payload);
        Objects.requireNonNull(occurredAt);
    }

    public static OutboxMessage from(OrderPaid event) {
        // Safe for these typed UUID/long/Instant values only.
        // Use a JSON codec when the schema adds arbitrary strings.
        String json = """
                {"eventId":"%s","orderId":"%s",
                 "orderVersion":%d,"occurredAt":"%s"}
                """.formatted(event.eventId(), event.orderId(),
                        event.orderVersion(), event.occurredAt());
        return new OutboxMessage(event.eventId(), event.orderId(),
                event.orderVersion(), "OrderPaid", 1,
                json, event.occurredAt());
    }
}

public interface OutboxRepository {
    // Use the supplied producer transaction; never commit here.
    void add(Connection c, OutboxMessage message)
            throws SQLException;
    // Read committed, pending rows; this simple relay has one worker.
    List<OutboxMessage> findUnpublished(int limit)
            throws SQLException;
    // Own short transaction; return only after its commit succeeds.
    void markPublished(UUID id, Instant time) throws SQLException;
}

A4 · Application handler

Java
public record PayOrderHandler(
        TransactionRunner transactions, OrderRepository orders,
        OutboxRepository outbox, Clock clock) {

    public void handle(PayOrder command) throws SQLException {
        transactions.inTransaction(c -> {
            Order order = orders.findForUpdate(c, command.orderId())
                    .orElseThrow(() ->
                            new IllegalArgumentException("Missing order"));
            if (!order.markPaid()) return null;
            orders.save(c, order);
            OrderPaid event = new OrderPaid(
                    UUID.randomUUID(), order.id(),
                    order.version(), clock.instant());
            outbox.add(c, OutboxMessage.from(event));
            return null;
        });
    }
}

A5 · Single-worker relay and scheduler

Java
public interface MessagePublisher {
    // Use aggregateId as the key. Return after broker acceptance
    // under the configured durability policy, not local enqueue.
    // Preserve id, payload, type, schema version on every retry.
    void publishAndAwaitAcceptance(OutboxMessage message)
            throws Exception;
}

public record OutboxRelay(
        OutboxRepository outbox, MessagePublisher publisher,
        Clock clock, System.Logger logger) {

    public void runOnce() throws SQLException, InterruptedException {
        for (OutboxMessage message : outbox.findUnpublished(100)) {
            try {
                publisher.publishAndAwaitAcceptance(message);
                outbox.markPublished(message.id(), clock.instant());
            } catch (InterruptedException ex) {
                Thread.currentThread().interrupt();
                throw ex;
            } catch (Exception ex) {
                logger.log(System.Logger.Level.WARNING,
                        "Retry required for " + message.id(), ex);
                // Stop this batch. No per-aggregate ordering promise.
                break;
            }
        }
    }

    public ScheduledFuture<?> schedule(
            ScheduledExecutorService scheduler) {
        return scheduler.scheduleWithFixedDelay(() -> {
            try {
                runOnce();
            } catch (InterruptedException ex) {
                Thread.currentThread().interrupt();
            } catch (Exception ex) {
                logger.log(System.Logger.Level.WARNING,
                        "Outbox poll failed", ex);
            }
        }, 0, 1, TimeUnit.SECONDS);
    }
}

A7 · JDBC inbox adapter

Java
public record JdbcInbox(Clock clock) implements InboxRepository {
    @Override
    public boolean tryInsert(
            Connection c, String consumer, UUID messageId)
            throws SQLException {
        String sql = """
                INSERT INTO inbox_message
                    (consumer_name, message_id, processed_at)
                VALUES (?, ?, ?)
                ON CONFLICT (consumer_name, message_id) DO NOTHING
                """;
        try (var statement = c.prepareStatement(sql)) {
            statement.setString(1, consumer);
            statement.setObject(2, messageId);
            statement.setTimestamp(3, Timestamp.from(clock.instant()));
            return statement.executeUpdate() == 1;
        }
    }
}

Appendix B · Adapter contracts

Keep the SQL boundary honest

The producer adapter methods receive the transaction’s connection. Their statements must not open another connection or commit on their own. The following SQL is PostgreSQL-specific; ? is a JDBC parameter placeholder.

For the consumer, JdbcInbox is implemented in Appendix A. The loyalty adapter must update the same consumer database in that transaction. Its application-specific customer mapping and loyalty schema remain a named port.

PostgreSQL 18 · producer transaction
-- OrderRepository.findForUpdate, on the handler's connection
SELECT id, status, version
FROM orders
WHERE id = ?
FOR UPDATE;

-- OrderRepository.save, on that SAME connection
UPDATE orders
SET status = ?, version = ?
WHERE id = ?;
-- Require exactly one affected row.

-- OutboxRepository.add, on that SAME connection
INSERT INTO outbox_message (
    id, event_type, event_version,
    aggregate_id, aggregate_version, payload, occurred_at
)
VALUES (?, ?, ?, ?, ?, CAST(? AS JSONB), ?);

Bind UUIDs with the driver’s UUID support, the payload as a string for the explicit JSONB cast, and the time as a supported timestamp value. Persist the complete event envelope; event_type and event_version travel with the payload to the consumer.

PostgreSQL 18 · relay operations
-- Relay read: committed rows only; one worker in this example
SELECT id, event_type, event_version,
       aggregate_id, aggregate_version, payload, occurred_at
FROM outbox_message
WHERE published_at IS NULL
ORDER BY occurred_at, id
LIMIT ?;

-- Separate short transaction AFTER observed broker acceptance
UPDATE outbox_message
SET published_at = ?
WHERE id = ? AND published_at IS NULL;

markPublished returns only after its own transaction commits. A failed response leaves the outcome uncertain, but retrying the marker is safe. If another attempt already marked the row, zero affected rows is a no-op; a missing row needs an explicit cleanup/recovery policy.
