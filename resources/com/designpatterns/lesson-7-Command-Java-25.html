Part 01

Derive the need

When does a method call stop being enough?

01Start without a pattern

An admin asks to ship an order. A controller calls a service. If execution is immediate and there are no extra requirements, this is a reasonable design.

The controller knows whom to call, and the service does the work now. No command object is needed yet.

02Pressure appears

Now the shipment request must be authorized, logged, retried after a temporary failure, handled by a background worker, or scheduled for tomorrow.

A direct call represents an invocation that is happening now. It gives us no separate application value meaning “ship order O123 later.” We can add wrappers around calls, but storing or transporting the request requires a representation of its own.

The design pressure

The request needs to survive beyond the moment at which the caller creates it.

03Separate intention from execution

There are two different moments: deciding what should happen, and attempting to make it happen. Give the first moment a value.

MomentRepresentationMeaning
Createnew ShipOrderCommand("O123")A request exists; shipping has not run.
Keep or passA variable, queue entry, or persisted messageThe request can wait or move elsewhere.
Executehandler.handle(command)The system now attempts the operation.

Command encapsulates a request as an object. Once the request has an identity and a representation, other code can decide when and how to execute it. [1]

04Make the request explicit

A Java record supplies a constructor, component accessors such as orderId(), and value-oriented equals, hashCode, and toString methods. Its component fields are final. Records are suitable for simple command data. [2]

Construction is not execution

This record has no shipping side effect. Records can have methods, but this design deliberately gives execution to a separate handler.

A record is only shallowly immutable: a final reference can still point to mutable data. These examples use String and UUID; copy mutable collections when a command contains them.

05Give execution to a handler

The command says what is requested. The handler coordinates how to attempt it. The service performs the work. You can still call the handler immediately; Command does not require a queue.

Part 02

Choose a representation

Should the request carry execution behavior or only data?

06Understand classic GoF Command

The classic form exposes an execution operation. The concrete command holds the receiver and the arguments it needs. An invoker calls the command without knowing the receiver’s specific operation. [1]

RoleIn this example
ClientCreates ShipOrderAction.
InvokerCalls execute().
Concrete commandShipOrderAction stores the request.
ReceiverOrderService performs shipping.

07Separate data from runtime dependencies

A live service reference is useful inside a process. It is a poor wire contract for another process. A remote worker needs command data and its own configured dependencies.

FormCarriesA useful fit
Classic commandArguments + receiver + execution methodLocal invokers, menus, reversible editor actions
Command + handlerData in the command; dependencies in the handlerApplication boundaries, queues, durable requests

This guide uses command data plus handlers for the backend example. That is a design choice, not a requirement of the pattern. A record is not automatically JSON, and it does not automatically implement Serializable. A transport still needs a codec and a defined schema. [2]

08Model commands and results

Once several operations share an execution boundary, describe the result type with Command<R>. We now add a stable command ID for the retry discussion later. These definitions replace the small record in section 4.

Here shipping returns a receipt, cancellation returns no useful value, and refund returns an ID. Void is a reference type used as a generic placeholder; a handler using it returns null. A domain result record is often more useful than that convention.

Imports for snippets: java.util.UUID and, where used, java.util.Objects. The complete program includes all imports and constructor validation.

09Tie each handler to one command type

C names the command the handler accepts; R names the result it returns. In the full example, ShippingUnitOfWork coordinates the order update and the stored retry result. The domain object still decides whether shipping is legal.

10See what the new boundary buys you

The request is now something you can inspect before executing it. You can validate its shape, check permissions, log selected metadata, serialize it, schedule it, or send it to a worker.

Capability is not a guarantee

A command object makes these behaviors possible. It does not provide durable storage, safe retries, authorization, or reliable event delivery by itself.

Each additional requirement needs an explicit owner and a failure policy. The next step is to give execution one boundary where such policies can compose.

Part 03

Build the execution boundary

Where should routing and shared policies live?

11Add logging with a decorator

This bus is synchronous: it returns the handler’s result or propagates a failure. A wrapper can preserve this interface while adding behavior.

The wrapper forwards to another bus, so logging can change without changing handlers. This is the Decorator idea applied to execution. The demo logs the command type, not its full payload; choose log fields deliberately.

12Keep routing knowledge in one place

A few commands can use explicit overloads or a small dispatcher. A dispatcher returning Object is also possible, but it does not satisfy the typed CommandBus interface above. Our complete example uses a registry that preserves the typed caller API.

Registration binds a concrete command class to a compatible handler. Lookup selects it by the command’s exact runtime class. Missing and duplicate registrations fail explicitly.

One contained type cast

A heterogeneous map cannot retain every command/result pair in its map type. The complete bus contains one documented unchecked result cast. The generic registration method maintains the relationship; raw types, parameterized command classes, and unchecked registrations are outside this example’s contract.

The input uses Class.cast for a runtime type check. [8] Configure the registry before use and treat it as fixed; the example does not implement concurrent registration.

13Keep the controller thin

The controller translates input into an application command and submits it. It does not implement shipping rules or select domain states.

Retry identity starts at the boundary

Generate a command ID once per intended operation and preserve it for retries. Creating a new random ID on every repeat HTTP request defeats deduplication by command ID. In a real API, validate the retry key and scope it to the authenticated tenant or operation.

Part 04

Protect domain ownership

A request, a rule, and a fact are different things.

14Distinguish commands from events

CommandEvent
MeaningPlease attempt an operation.A named fact occurred.
ExampleShipOrderCommandOrderShipped
TimingBefore execution; may be rejectedAfter the defined change succeeds
Default ownershipOne logical responsible handlerZero or more interested subscribers

“One handler” means one logical owner, not one worker instance. Several workers may compete to process requests. An event consumer may still fail even though the event describes a completed change.

Name the fact precisely

This lesson models SHIPPED as a domain status. A database update does not prove physical carrier pickup. In a real system, use a more precise event such as ShipmentRequested or ShipmentBooked when that is the fact you can establish.

15Connect Command to State

State governs what an order can legally do at its current lifecycle stage. Command represents the attempt to do it. The handler loads the order, asks it to ship, and saves the outcome within the chosen unit of work.

This three-line workflow does not yet supply transactions, duplicate detection, or concurrency control. Those belong to its surrounding execution boundary.

OwnerResponsibility
CommandRequested operation and its input data
HandlerCoordinates the application use case
OrderEnforces legal domain transitions
Repository / unit of workLoads and persists the changes consistently

16Keep business invariants in the domain

The handler calls ship() instead of assigning a new status itself. Here the immutable aggregate returns a new order, so the caller must use that return value.

An enum and a small condition are enough for this reduced model. Full State objects become useful when state-specific behavior grows. Encapsulation has a concrete purpose: make the transition rule hard to bypass through the application’s normal API.

Part 05

Separate execution in time

What changes when a request waits, fails, or arrives twice?

17Put data on a queue

A producer can encode the command, hand it to a queue, and let a worker decode it and call the handler later. The producer and worker no longer have to execute in the same call stack.

The envelope identifies the message type and schema version. The handler’s service or repository dependencies are created by the receiving application. The JSON shown is a contract illustration; no JSON library or broker is required by the runnable program.

  1. Producer validates and submits the request.
  2. Queue retains a message according to its delivery contract.
  3. Worker decodes it and attempts the use case.
  4. Worker acknowledges after the required durable work succeeds.

18Change the promise made to the caller

Synchronous completionAsynchronous acceptance
The call waits for a result or failure.The caller receives confirmation of acceptance.
A successful response can describe the completed work.Later execution may succeed, fail, or be rejected.
ShipmentReceipt is a possible result.Return a request ID and a way to inspect its status.

HTTP 202 Accepted means processing has been accepted but is not complete; it does not guarantee eventual execution. The response should describe the current status and provide a way to monitor it. [4]

Accepted and completed are separate states

Do not label the order “shipped” merely because its command entered a queue. Also define what happens if the producer cannot tell whether submission succeeded.

19Derive the retry problem

Imagine a worker creates a shipment successfully, then crashes before acknowledging the message. A delivery system that redelivers unacknowledged work may send that command again.

StepBusiness effectQueue knowledge
First execution succeedsShipment exists.Message is still unacknowledged.
Worker crashesShipment still exists.Completion was not confirmed.
Message is retriedA second effect is possible.Worker must decide how to handle a repeat.

The problem is uncertainty at a boundary. Retrying can recover missing work or repeat work that already happened. Know the broker’s delivery contract, and design the handler for the repeats it permits.

20Give repeated delivery one business effect

For this use case, idempotent handling means repeating the same logical request does not create an additional shipment. The command carries a stable ID; the handler can return the previously stored result.

Reuse the ID for a retry of the same intention. Reject an ID reused with different input. Persist the result when callers need the same answer again. A new ID means a new request, even if its payload happens to match.

The key is only an identifier

A command ID does not make the work atomic. Two workers can both see “not processed”; a crash can occur after the effect but before the ID is recorded.

21Choose a reliable atomic boundary

The sequence “check, perform work, mark processed” has both a race window and a crash window. For updates in one database, a possible design is:

  1. Begin a transaction and claim a command key protected by a unique constraint, scoped to the application or tenant as needed.
  2. Verify the stored payload matches any repeated request. Return the stored result for a completed repeat.
  3. Apply the business update with appropriate concurrency control, and persist the result and an outbox event in the same transaction.
  4. Commit. Acknowledge the message only after the durable work succeeds. Publish outbox events separately; their consumers must also tolerate duplicates.

The outbox pattern addresses the database-update/message-publish gap by recording pending events with the business change. It still requires duplicate-aware consumption. [5]

External effects need their own design

A local transaction cannot atomically include an arbitrary carrier API call. If a provider supports idempotency keys, preserve the same key across attempts and verify its scope and retention contract. Otherwise use reconciliation or a workflow that can resolve uncertain outcomes.

Deduplication and lifecycle rules answer different questions. Deduplication asks “did this same request already finish?” State asks “is this new request legal now?” Both can be necessary.

Part 06

Add policies and reversibility

Which concerns surround execution, and which actions can be reversed?

22Authorize using trusted context

A command tells you what someone wants. It does not prove they may do it. Authorize the operation and target resource using identity established by the application’s trusted authentication boundary. [6]

A userId field is not authentication

Do not trust a client-supplied actor or permission flag. The wrapper above must receive its actor from trusted server code and must not be reused across different users. For queued work, define how trusted identity is conveyed and whether authorization is checked again at execution.

23Validate at the right layer

Validation is not one undifferentiated check. Different owners know different facts.

CheckExampleOwner
Input shapeRequired ID; amount is positiveDecoder / command constructor
PermissionActor may ship this orderAuthorization policy with trusted context
Business invariantOnly a packed order can shipDomain model
Concurrent consistencyOrder did not change before the writeTransaction / persistence mechanism

A possible pipeline validates input, authorizes the target, logs selected metadata, starts a transaction, invokes the handler, and commits. An outer observation layer may record rejected attempts too. Choose ordering based on what each step must know.

Log “completed” only at the boundary that knows the required commit succeeded. In the runnable example, the logging wrapper observes an in-memory operation, not a database commit.

24Use undo when you can restore the relevant state

Classic Command can expose undo behavior. [1] A small editor example makes the contract clearer than pretending every external action has an inverse.

This assumes one editor owns the buffer and commands are undone in reverse execution order. Otherwise restoring an old snapshot may overwrite intervening edits. The captured before value plays the role of a small memento.

25Distinguish undo from compensation

OperationPossible responseWhat it means
Local text replacementRestore the previous bufferUndo, under the editor’s ownership rules
Payment chargeIssue a refundA new business operation compensates for the charge
Email already deliveredSend a correctionThe original external observation remains

Compensation is application-specific work and can itself fail. It may need retries and does not necessarily restore the exact original state. [7]

Command does not imply reversibility

An explicit request helps store and execute actions. Whether a particular action can be undone depends on its domain and on what the outside world has already observed.

Part 07

Distinguish the nearby patterns

Identify the design pressure, not just the interface shape.

26Command versus Strategy

QuestionStrategyCommand
What varies?The algorithm used for an operationThe requested operation and its arguments
ExampleStandard or express pricing calculationShip order O123
What does the caller choose?How to calculate a shipping priceWhich action to request
Can they compose?A handler may use a pricing strategy.The command remains the requested action.

A method named execute() is not enough to identify Command. Ask whether the object represents a request that can be passed around independently of its execution.

27Command versus Observer

Command asks a responsible component to attempt work. Observer arranges for interested objects to receive notifications. A command may produce an event, and several observers may react to that event.

CommandObserver / event notification
ShipOrderCommand requests work.OrderShipped reports a defined completed change.
One logical handler owns the use case.Email, analytics, and tracking consumers own their reactions.

Classic Observer is often local object notification. A durable event broker adds transport, persistence, retries, and delivery semantics. The same conceptual distinction applies, but those reliability properties do not come from Observer itself.

28Command versus Factory

Factory answers a construction question: which object should be created and how should it be configured? Command answers a request question: what operation has been asked for?

A factory or dependency-injection setup might construct a ShipOrderHandler with the right repository. A controller constructs a ShipOrderCommand containing the input for one use case. Creation and execution remain different responsibilities.

Part 08

Assemble the design

Use only the structure justified by the requirements.

29Trace a realistic application flow

OrderOwnerWhat happens
1API adapterReads input and obtains trusted caller context.
2CommandRepresents ShipOrder with a stable request ID.
3Execution policiesValidate, authorize, and record appropriate metadata.
4Handler / unit of workCoordinates duplicate checks and loads the order.
5DomainEnforces the lifecycle transition.
6TransactionPersists state, result, and pending event together.
7Event deliveryPublishes the event for interested consumers.

Validation and authorization are ordered checks, not parallel branches that later merge. A queue may sit between request submission and worker execution; if it does, the API response describes acceptance and the worker owns eventual execution.

30Make one coherent implementation

The complete program assembles the command, typed registry, logging decorator, controller, handler, domain rule, and stored-result behavior. Save the embedded source as CommandLesson.java.

What the program proves

It checks successful shipping, repeat delivery, payload mismatch for a reused key, an illegal lifecycle transition, a missing order, invalid input, missing routing, and duplicate registration.

The store builds a new immutable snapshot containing the order, result, and event, then replaces one reference inside a synchronized method. That keeps this small in-process model consistent for callers of that store.

Scope of the runnable model

It has no durable database, broker, external carrier, authentication system, or cross-process lock. Restarting loses its data. Its list of events is not a durable outbox. The constructors represent trusted setup or rehydration; a production API must not expose arbitrary status construction.

The lesson’s production discussion is therefore a design checklist, not a claim that this in-memory example implements distributed exactly-once effects.

31Recognize overengineering

An ordinary calculator.add(2, 3) does not need a command, handler, registry, and pipeline merely because those abstractions are available. A direct call can already be validated, logged, or authorized when that is all you need.

Use Command when giving the request itself a lifecycle makes the system clearer: passing it around, queuing it, storing it, scheduling it, replaying it deliberately, or separating its caller from its executor.

A useful progression is a direct call, then an explicit command with one handler, then an execution boundary when shared policies justify it. A bus is optional. A distributed queue is a separate decision.

32Apply the first-principles decision process

  1. What concrete requirement is hard with a direct call?
  2. Must the request exist independently of execution?
  3. What data identifies the requested action, its input, and a repeat?
  4. Who decides when it runs, and who owns the business rules?
  5. What does the caller learn: accepted, completed, or failed?
  6. If delivery repeats or the process crashes, which effect must remain singular?
  7. Does an explicit command type make these decisions easier to understand?
The lesson to retain

Command gives an intention a representation. The hard design work is assigning ownership, defining execution timing, preserving business invariants, and deciding what a retry means.

Part 09

Practice: transfer money

Build the boundary before adding a queue.

This is a software-design exercise with an in-memory, single-currency model. Start with BankService.transfer(from, to, cents), then introduce a command and handler only as the requirements demand.

Your design decisions

DecisionDefine before implementation
InputPositive amount, required account IDs, distinct source and destination
DomainNo overdraft; checked arithmetic; both accounts use the modeled currency
AtomicityDebit, credit, command result, and event succeed together
RetrySame key + same payload returns one result; changed payload is rejected
ConcurrencyCompeting transfers cannot both spend the same available balance
APIExplicitly choose synchronous completion or asynchronous acceptance

Acceptance criteria

  1. The command contains data, with no live service dependencies.
  2. The handler coordinates the use case; account behavior owns balance invariants.
  3. A failed debit or credit leaves both balances unchanged.
  4. A repeated command ID cannot transfer money twice, including concurrent delivery.
  5. Reusing a command ID with different input fails explicitly.
  6. Define an explicit message schema and round-trip it through your chosen codec.
  7. MoneyTransferred describes committed success and is emitted once in the local model; distributed consumers tolerate redelivery.
  8. If you add a queue, make acceptance and completion separately observable.

Test cases to write

CaseExpected outcome
Transfer 250 from balances 1,000 and 100Balances 750 and 350; one result and one logical event
Repeat the same commandBalances unchanged; original result returned
Same key, different amountRejected; balances unchanged
Insufficient funds or overflowRejected; neither account is modified
Two competing debits exceed the balanceAt most the affordable work succeeds; balance stays valid
Crash before durable commit / after commit before acknowledgementRollback / retry returns the committed result
Reasoning guide · open after designing your solution

Use one unit of work spanning both accounts and the command result. Inside it, enforce the command key’s uniqueness, compare repeated input, invoke domain operations, and commit a consistent result. Give the accounts private state or immutable values so callers cannot silently skip the balance rules.

An in-memory lock can model concurrency only within one process. A durable implementation needs database transactions and appropriate locking or conflict detection. External payment networks introduce another boundary; this exercise does not implement those integrations.

Start by testing the handler and domain synchronously. Add serialization, queue submission, worker acknowledgement, and recovery behavior only after the local contract is clear.
