Before the first lesson

This guide assumes you have used Java 8 but want to rebuild your understanding from the ground up. Every code lesson presents a complete source file first, then commands, expected behavior, principles, a trap, and an exercise with an answer.

Your endpoint is Java 25.

Java 26 is already generally available as of this guide’s verification date. Java 25 is the requested endpoint and Oracle’s current LTS release. The lessons deliberately stop at 25.

What “all features” means here

The release index covers every JEP listed for JDK 9–25: language changes, libraries, previews, incubators, JVM changes, tools, ports, removals, and JDK build/test work. The lessons go deeper on features you use directly in application code. Smaller implementation changes have concise explanations in each release’s index.   3. Run the displayed commands from that directory. Ordinary examples target the stated minimum release; current JDK 25 can compile those older permanent language/API surfaces with --release. This does not emulate historical JVM behavior.
  4. Preview examples require JDK 25 specifically, with preview enabled during compilation and launch. The source bundle includes an optional Python 3 runner: python3 run_examples.py.

Lesson 8.1

Values, objects, lambdas, and streams

Permanent · Java 8+Executed · JDK 17 / release 8
Baseline.java
import java.util.Arrays;
import java.util.List;
import java.util.stream.Collectors;
public class Baseline {
    public static void main(String[] args) {
        List<String> names = Arrays.asList("Ada", "Lin", "Alexander");
        List<String> result = names.stream()
            .filter(name -> name.length() <= 3)
            .map(String::toUpperCase)
            .collect(Collectors.toList());
        System.out.println(result);
        System.out.println(names);
    }
}
Compile and run
javac --release 8 Baseline.java
java Baseline
Expected standard output
[ADA, LIN]
[Ada, Lin, Alexander]

From first principles

A variable has a compile-time type. An object has a runtime class. A reference variable holds a reference to an object; assigning it does not copy that object. A lambda supplies behavior for a functional interface: an interface with one abstract method. Here filter receives a predicate and map receives a function. A stream describes a pipeline over elements. Intermediate operations are lazy; collect is the terminal operation that requests the work. This pipeline creates a new result rather than changing names. javac translates source into class files; java loads those files and executes them on a JVM, which may interpret code and compile hot code into machine instructions.

The trap

Arrays.asList is fixed-size but allows replacing elements; it is not an immutable list. A stream is single-use. Side effects inside pipelines make ordering and parallel execution harder to reason about.

Try it

Change the filter to keep names longer than three characters. Predict both printed lists.

Check your reasoning

The result is [ALEXANDER]. The original names list is unchanged.

Official references: Stream · Arrays

Lesson 9.1

Collection factories and their contracts

Permanent · Java 9+Executed · JDK 17 / release 9
Collections9.java
import java.util.List;
import java.util.Map;
import java.util.Set;
public class Collections9 {
    public static void main(String[] args) {
        List<String> names = List.of("Ada", "Lin");
        Set<String> roles = Set.of("reader", "writer");
        Map<String, Integer> stock = Map.of("pen", 3, "book", 2);
        System.out.println(names);
        System.out.println(roles.contains("reader"));
        System.out.println(stock.get("pen"));
        try { names.add("Sam"); }
        catch (UnsupportedOperationException e) {
            System.out.println("unmodifiable");
        }
    }
}
Compile and run
javac --release 9 Collections9.java
java Collections9
Expected standard output
[Ada, Lin]
true
3
unmodifiable

From first principles

A collection owns a structure of references. List.of, Set.of, and Map.of construct small unmodifiable collections directly. List preserves encounter order. Set and Map do not promise the printed iteration order you may happen to observe. Map.ofEntries accepts entry objects and scales beyond the fixed-arity Map.of overloads. Factories remove the old create-then-wrap ceremony.

The trap

These factories reject null. Set.of rejects duplicate elements; Map.of rejects duplicate keys. Unmodifiable structure is not deep immutability: a mutable object stored inside can still change.

Try it

Can List.of(new StringBuilder("a")) change visibly without adding or replacing an element?

Check your reasoning

Yes. Calling append on its StringBuilder changes that object; the list structure stays unmodifiable.

Official references: List · Set · Map

Lesson 9.2

Prefix operations and Optional as a stream

Permanent · Java 9+Executed · JDK 17 / release 9
Streams9.java
import java.util.List;
import java.util.Optional;
import java.util.stream.Collectors;
import java.util.stream.Stream;
public class Streams9 {
    public static void main(String[] args) {
        System.out.println(Stream.of(1, 2, 0, 3)
            .takeWhile(n -> n > 0).collect(Collectors.toList()));
        System.out.println(Stream.of(1, 2, 0, 3)
            .dropWhile(n -> n > 0).collect(Collectors.toList()));
        List<Optional<String>> values =
            List.of(Optional.of("Ada"), Optional.empty());
        System.out.println(values.stream().flatMap(Optional::stream)
            .collect(Collectors.toList()));
        System.out.println(Stream.iterate(1, n -> n < 4, n -> n + 1)
            .collect(Collectors.toList()));
        System.out.println(Stream.ofNullable(null).count());
        System.out.println(Optional.<String>empty()
            .or(() -> Optional.of("fallback")).get());
    }
}
Compile and run
javac --release 9 Streams9.java
java Streams9
Expected standard output
[1, 2]
[0, 3]
[Ada]
[1, 2, 3]
0
fallback

From first principles

filter checks every element independently. On an ordered stream, takeWhile retains the longest initial matching prefix, whereas dropWhile removes that prefix. Three-argument iterate expresses start, continuation condition, and next value. ofNullable creates zero or one elements. Optional.stream turns absence into an empty stream, making flatMap a natural way to discard missing values. Optional.or supplies another Optional lazily; ifPresentOrElse adds an explicit empty branch.

The trap

takeWhile is not filter: the trailing 3 is never reconsidered. Ordered parallel prefix operations can be expensive. Optional is a return-value tool, not a universal replacement for every nullable field.

Try it

What does filter(n -> n > 0) produce for the same input?

Check your reasoning

[1, 2, 3]. It evaluates the predicate for the trailing element too.

Official references: Stream · Optional

Lesson 9.3

Private interface helpers and resource ownership

Permanent · Java 9+Executed · JDK 17 / release 9
Language9.java
import java.io.StringReader;
import java.util.ArrayList;
public class Language9 {
    interface Greeting {
        default String greet(String name) { return prefix() + name; }
        private String prefix() { return "Hello, "; }
    }
    public static void main(String[] args) throws Exception {
        Greeting greeting = new Greeting() {};
        System.out.println(greeting.greet("Ada"));
        StringReader reader = new StringReader("A");
        try (reader) {
            System.out.println((char) reader.read());
        }
        ArrayList<String> names = new ArrayList<>() {};
        names.add("Lin");
        System.out.println(names);
    }
}
Compile and run
javac --release 9 Language9.java
java Language9
Expected standard output
Hello, Ada
A
[Lin]

From first principles

An interface can share implementation privately between its default or static methods without exposing a new public operation. try-with-resources calls close when its block ends, including on exceptions. Java 9 allows an existing final or effectively final variable in the resource list. Diamond inference now works for eligible anonymous classes. @SafeVarargs also becomes legal on private instance methods.

The trap

The variable in try(reader) must not be reassigned. An underscore by itself stops being a legal identifier in Java 9; its later use as an unnamed variable is a different feature. A @SafeVarargs annotation is a promise you must actually justify.

Try it

Why is a private interface helper preferable to another default method for prefix?

Check your reasoning

It avoids adding an overridable public operation merely to share implementation.

Lesson 9.4

Processes, stack walking, and version information

Permanent · Java 9+Executed · JDK 17 / release 9

public class Runtime9 {
    static String caller() {
        return StackWalker.getInstance().walk(frames ->
            frames.skip(1).findFirst().get().getMethodName());
    }
    public static void main(String[] args) {
        ProcessHandle self = ProcessHandle.current();
        System.out.println(self.pid() > 0);
        System.out.println(self.equals(ProcessHandle.current()));
        System.out.println(caller());
        System.out.println(Runtime.version().major() >= 9);
    }
}
Compile and run
javac --release 9 Runtime9.java
java Runtime9
Expected standard output
true
true

From first principles

A ProcessHandle identifies an operating-system process; info returns metadata as Optional values because information can be unavailable. onExit gives a CompletableFuture for termination. StackWalker lets you inspect stack frames through a lazy stream confined to the walk callback. Runtime.version returns structured version information instead of making you parse arbitrary strings. Java 10 later introduces feature/interim/update/patch naming; major is used here for Java 9 compatibility.

The trap

Do not assume process metadata is always present. A PID can be reused after a process exits. Stack inspection costs work; use it for diagnostics, not routine business decisions.

Try it

Why should process.info().command() be treated as Optional?

Check your reasoning

Permissions, operating-system behavior, and process lifetime can prevent obtaining it.

Lesson 9.5

Future timeouts do not stop the work

Permanent · Java 9+Executed · JDK 17 / release 9
Async9.java
import java.util.concurrent.CompletableFuture;
import java.util.concurrent.TimeUnit;
public class Async9 {
    public static void main(String[] args) {
        CompletableFuture<String> missing = new CompletableFuture<>();
        System.out.println(missing.completeOnTimeout(
            "fallback", 10, TimeUnit.MILLISECONDS).join());
        CompletableFuture<String> ready =
            CompletableFuture.completedFuture("ready");
        System.out.println(ready.copy().join());
    }
}
Compile and run
javac --release 9 Async9.java
java Async9
Expected standard output
fallback
ready

From first principles

A future represents a result that may arrive later. completeOnTimeout supplies a normal fallback if the future has not completed; orTimeout completes it exceptionally instead. delayedExecutor schedules submission after a delay. copy and minimalCompletionStage help expose an observation-oriented boundary without handing out the original mutable future.

The trap

Timeout changes completion state; it does not generally cancel the operation producing that result. Design cancellation and resource cleanup separately. Avoid blocking a shared executor with long blocking calls.

Try it

Replace completeOnTimeout with orTimeout. What changes?

Check your reasoning

join throws CompletionException whose cause is TimeoutException; no fallback value is produced.

Official references: CompletableFuture

Lesson 9.6

Publish, subscribe, and request demand

Permanent · Java 9+Executed · JDK 17 / release 9
Flow9.java
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.Flow;
import java.util.concurrent.SubmissionPublisher;
import java.util.concurrent.TimeUnit;
public class Flow9 {
    public static void main(String[] args) throws Exception {
        CountDownLatch done = new CountDownLatch(1);
        try (SubmissionPublisher<String> publisher =
                 new SubmissionPublisher<>()) {
            publisher.subscribe(new Flow.Subscriber<String>() {
                public void onSubscribe(Flow.Subscription s) {
                    s.request(Long.MAX_VALUE);
                }
                public void onNext(String item) {
                    System.out.println(item);
                }
                public void onError(Throwable error) {
                    error.printStackTrace(); done.countDown();
                }
                public void onComplete() { done.countDown(); }
            });
            publisher.submit("event");
        }
        if (!done.await(5, TimeUnit.SECONDS)) {
            throw new IllegalStateException("subscriber timed out");
        }
    }
}
Compile and run
javac --release 9 Flow9.java
java Flow9
Expected standard output
event

From first principles

Flow defines Publisher, Subscriber, Subscription, and Processor contracts. The subscriber declares demand with request; this allows the producer and consumer to coordinate delivery. SubmissionPublisher is a JDK implementation useful for learning and simple asynchronous publication. Closing it signals completion after its pending items are handled.

The trap

This example requests unbounded demand for clarity. A real slow subscriber should request bounded batches and replenish demand. Flow supplies interfaces, not a complete reactive application framework.

Try it

What happens if onSubscribe never requests anything?

Check your reasoning

The subscriber has no demand, so onNext is not entitled to receive an item.

Official references: Flow · SubmissionPublisher

Lesson 9.7

Atomic access without Unsafe

Permanent · Java 9+Executed · JDK 17 / release 9
VarHandle9.java
import java.lang.invoke.MethodHandles;
import java.lang.invoke.VarHandle;
public class VarHandle9 {
    private int count;
    public static void main(String[] args) throws Exception {
        VarHandle handle = MethodHandles.lookup()
            .findVarHandle(VarHandle9.class, "count", int.class);
        VarHandle9 counter = new VarHandle9();
        System.out.println(handle.compareAndSet(counter, 0, 1));
        System.out.println(handle.getVolatile(counter));
    }
}
Compile and run
javac --release 9 VarHandle9.java
java VarHandle9
Expected standard output
true
1

From first principles

A race occurs when threads access shared state without the required coordination. VarHandle describes a typed access path to a field or array element and offers ordinary, volatile, acquire/release, and atomic operations. compareAndSet changes the field only when its current value matches the expected value, as one atomic operation. Here we demonstrate its contract without requiring a nondeterministic race.

The trap

Atomic access to one field does not make a multi-field invariant atomic. Use higher-level locks or atomic classes when they express the design more clearly. Thread.onSpinWait is only a spin-loop hint, not synchronization.

Try it

What does a second compareAndSet(counter, 0, 1) return?

Check your reasoning

false: the current value is already 1.

Official references: VarHandle · Thread

Lesson 9.8

Small APIs that remove common boilerplate

Permanent · Java 9+Executed · JDK 17 / release 9
MoreApis9.java
import java.io.ByteArrayInputStream;
import java.nio.charset.StandardCharsets;
import java.util.Arrays;
import java.util.Objects;
import java.util.stream.Collectors;
import java.util.stream.Stream;
public class MoreApis9 {
    public static void main(String[] args) throws Exception {
        byte[] bytes = new ByteArrayInputStream(
            "hello".getBytes(StandardCharsets.UTF_8)).readAllBytes();
        System.out.println(new String(bytes, StandardCharsets.UTF_8));
        System.out.println(Objects.requireNonNullElse(null, "default"));
        System.out.println(Arrays.mismatch(new int[]{1, 2}, new int[]{1, 3}));
        System.out.println(Stream.of("a b", "c")
            .collect(Collectors.flatMapping(
                s -> Arrays.stream(s.split(" ")), Collectors.toList())));
    }
}
Compile and run
javac --release 9 MoreApis9.java
java MoreApis9
Expected standard output
hello
default
1
[a, b, c]

From first principles

InputStream adds readAllBytes, readNBytes, and transferTo; choose streaming for large data. Objects adds null-fallback and index/range checks. Arrays adds comparison and first-mismatch operations. Collectors.filtering and flatMapping apply transformations inside a downstream collector, especially useful after groupingBy. Other additions include Matcher.results, date streams via LocalDate.datesUntil, and streams of Scanner tokens.

The trap

readAllBytes must fit in memory. A downstream filtering collector can retain a group with no accepted elements; filtering before grouping may omit the group entirely.

Try it

Why can Objects.requireNonNullElseGet be cheaper than requireNonNullElse?

Check your reasoning

Its supplier computes the default only if the first argument is null.

From first principles

A package groups types; a module groups packages and declares a boundary. requires establishes readability of another module. exports makes public types in a package accessible to readers. opens allows deep reflection and is a different permission. java.base is implicitly required. guide.app is not exported, so the implementation remains inside the module. Class-path applications belong to an unnamed module and can migrate incrementally. For service loading, a consumer declares uses and a provider declares provides ... with; requires transitive passes readability to consumers, while requires static is a compile-time dependency that is optional at run time. Try removing exports guide.api after adding a second consumer module: public alone is not enough across module boundaries.

Lesson 11.2

Permanent · Java 11+Executed · JDK 17 / release 11
Http11.java
import com.sun.net.httpserver.HttpServer;
import java.net.InetSocketAddress;
import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.nio.charset.StandardCharsets;
import java.time.Duration;
public class Http11 {
    public static void main(String[] args) throws Exception {
        HttpServer server = HttpServer.create(
            new InetSocketAddress("127.0.0.1", 0), 0);
        server.createContext("/hello", exchange -> {
            byte[] body = "hello".getBytes(StandardCharsets.UTF_8);
            exchange.sendResponseHeaders(200, body.length);
            try (var out = exchange.getResponseBody()) { out.write(body); }
        });
        server.start();
        try {
            var client = HttpClient.newBuilder()
                .connectTimeout(Duration.ofSeconds(5)).build();
            var request = HttpRequest.newBuilder(URI.create(
                "http://127.0.0.1:" + server.getAddress().getPort() + "/hello"))
                .timeout(Duration.ofSeconds(5)).GET().build();
            var response = client.send(request,
                HttpResponse.BodyHandlers.ofString());
            System.out.println(response.statusCode());
            System.out.println(response.body());
        } finally { server.stop(0); }
    }
}

From first principles

final fixes a field’s assignment during initialization. A stable value separates creating a holder from assigning its contents later, at most once successfully. orElseSet performs lazy initialization with concurrency coordination. From first principles

A task often needs results from several child tasks. A structured scope owns those tasks and prevents them outliving the block. In Java 25, open creates a scope whose default policy fails when any subtask fails and cancels unfinished siblings; join waits for the relevant outcome. Read successful subtask values after join. Lesson 25.11

Capstone: process orders using permanent features

Permanent · Java 25+⚠ Not executed here · specification reviewed
Capstone25.java
import java.util.List;
import java.util.ArrayList;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;
public class Capstone25 {
    record Order(String id, int amount) {}
    sealed interface Outcome permits Accepted, Rejected {}
    record Accepted(String id, int total) implements Outcome {}
    record Rejected(String id, String reason) implements Outcome {}
    static final ScopedValue<String> REQUEST = ScopedValue.newInstance();
    static Outcome process(Order order) {
        if (order.amount() < 0) {
            return new Rejected(REQUEST.get(), "negative amount");
        }
        return new Accepted(REQUEST.get(), order.amount());
    }
    static String describe(Outcome outcome) {
        return switch (outcome) {
            case Accepted(var id, var total) -> id + " accepted " + total;
            case Rejected(var id, var reason) -> id + " rejected " + reason;
        };
    }
    public static void main(String[] args) throws Exception {
        var orders = List.of(new Order("A1", 20), new Order("A2", -1));
        try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
            var results = new ArrayList<Future<Outcome>>();
            for (var order : orders) {
                results.add(executor.submit(() ->
                    ScopedValue.where(REQUEST, order.id())
                        .call(() -> process(order))));
            }
            for (var result : results) {
                System.out.println(describe(result.get()));
            }
        }
    }
}
Compile and run
javac --release 25 Capstone25.java
java Capstone25
Expected standard output
A1 accepted 20
A2 rejected negative amount

From first principles

This small application combines unmodifiable inputs, local inference, records, a sealed outcome model, record-pattern switch, virtual threads, and scoped values. Each task establishes its own context binding; the executor does not inherit the caller’s scoped bindings automatically. Retrieving futures in input order makes the displayed output deterministic even when tasks finish in another order. No preview features are used.

The trap

The computation is deliberately tiny, so virtual threads offer no performance advantage here. Replace process with a real waiting operation to explore its concurrency use case. For a failure-sensitive group of related tasks, study structured concurrency separately; this permanent-API example does not provide its sibling cancellation policy.

Check your reasoning
